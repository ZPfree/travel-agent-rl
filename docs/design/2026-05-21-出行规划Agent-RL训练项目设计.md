# 出行规划Agent RL训练项目设计文档

## 1. 项目概述

### 1.1 背景
以真实出行规划为背景，通过强化学习（RL）提升Agent在复杂环境、多约束条件下的任务规划与执行能力。

### 1.2 核心目标
- 实现Long Horizon Agent，支持最高50次工具调用
- 支持8种工具接口（高德、Google、Tavily等）
- 支持2~5个约束条件的同时优化
- 完整的从0到1训练流程

### 1.3 技术栈

| 组件 | 选择 | 版本 |
|------|------|------|
| 基础模型 | Qwen3-0.6B | - |
| Agent框架 | LangGraph | 1.0 |
| RL框架 | TRL | 最新版 |
| 训练方式 | PPO + DPO | - |
| 训练环境 | 单机单卡 | RTX 4090 |
| 工具数据 | 模拟数据 | - |

## 4. Agent层设计（LangGraph）

### 4.1 状态定义

```python
from typing import TypedDict, Annotated, List, Dict, Any
from langgraph.graph.message import add_messages

class Constraint(TypedDict):
    type: str          # time, budget, people, preference
    value: str
    weight: float

class ToolCall(TypedDict):
    tool_name: str
    parameters: Dict[str, Any]
    result: Any
    step: int

class TravelState(TypedDict):
    # 输入
    query: str
    constraints: List[Constraint]

    # 过程
    messages: Annotated[list, add_messages]
    tool_calls: List[ToolCall]
    current_plan: str
    step_count: int
    max_steps: int

    # 约束追踪
    constraint_satisfaction: Dict[str, float]

    # 输出
    final_plan: str
    is_complete: bool
```

### 4.2 状态图定义

```python
from langgraph.graph import StateGraph, END

def create_travel_agent():
    workflow = StateGraph(TravelState)

    # 添加节点
    workflow.add_node("analyze", analyze_node)      # 分析需求
    workflow.add_node("think", think_node)          # 思考决策
    workflow.add_node("use_tool", tool_node)        # 使用工具
    workflow.add_node("update_plan", plan_node)     # 更新规划
    workflow.add_node("check_constraints", check_node)  # 检查约束

    # 定义边
    workflow.set_entry_point("analyze")
    workflow.add_edge("analyze", "think")
    workflow.add_conditional_edges(
        "think",
        should_use_tool,
        {
            "use_tool": "use_tool",
            "update_plan": "update_plan"
        }
    )
    workflow.add_edge("use_tool", "update_plan")
    workflow.add_edge("update_plan", "check_constraints")
    workflow.add_conditional_edges(
        "check_constraints",
        should_continue,
        {
            "continue": "think",
            "end": END
        }
    )

    return workflow.compile()
```

### 4.3 Long Horizon Agent（支持最高50次工具调用）

#### 4.3.1 设计目标

在真实出行规划场景中，完成一个复杂任务（如"五天四晚华东五市家庭游"）通常需要 20~50 次工具调用（POI搜索、路线规划、天气查询、日历检查等）。本项目要求 Agent 在 50 步工具调用范围内稳定完成任务，且不出现上下文溢出、决策退化或工具调用失败累积。

#### 4.3.2 工具调用成功率保障机制

**1. 工具调用重试策略**

```python
class ToolRetryPolicy:
    max_retries: int = 3           # 最大重试次数
    base_delay: float = 1.0        # 基础延迟（秒）
    backoff_factor: float = 2.0    # 指数退避因子
    retryable_errors: List[str] = [  # 可重试错误类型
        "timeout", "rate_limit", "network_error", "service_unavailable"
    ]
```

重试流程：
```
工具调用 → 失败 → 判断是否可重试
                    ├─ 可重试 → 等待(base_delay × backoff^attempt) → 重试（最多3次）
                    └─ 不可重试 → 返回降级结果 + 错误标记
```

**2. 工具调用降级策略**

当工具调用多次失败后，采用降级方案：

| 工具 | 降级方案 | 降级数据来源 |
|------|----------|-------------|
| `amap_poi_search` | 使用缓存的热门POI | 本地预置数据 |
| `amap_route_plan` | 使用直线距离估算 | 几何计算 |
| `weather_query` | 使用历史同期天气 | 历史均值 |
| `google_search` | 切换到 `tavily_search` | 备用搜索引擎 |
| `calendar_query` | 返回"无日程冲突" | 默认空闲 |

**3. 工具调用参数校验**

在调用工具前，对参数进行格式校验，避免因参数错误导致的无效调用：

```python
class ToolCallValidator:
    def validate(self, tool_name: str, params: Dict) -> Tuple[bool, Optional[str]]:

        return is_valid, error_message
```

**4. 工具调用结果置信度**

每个工具返回结果附带置信度分数，Agent 据此决定是否需要交叉验证：

```python
class ToolResult(BaseModel):
    success: bool
    data: Any
    confidence: float           # 0.0 ~ 1.0
    error: Optional[str] = None

# Agent 决策逻辑：
# confidence >= 0.8 → 直接使用
# 0.5 <= confidence < 0.8 → 使用但标记为低置信
# confidence < 0.5 → 重新调用或使用备用工具交叉验证
```

**5. 工具调用成功率指标**

训练过程中实时监控以下指标：

| 指标 | 计算方式 | 目标值 |
|------|----------|--------|
| 单次调用成功率 | 成功调用数 / 总调用数 | ≥ 95% |
| 重试后成功率 | (成功 + 重试成功) / 总调用数 | ≥ 99% |
| 降级触发率 | 降级调用数 / 总调用数 | ≤ 5% |
| 平均调用延迟 | 总延迟 / 调用次数 | ≤ 2s |

#### 4.3.3 长程上下文管理

**1. 上下文窗口策略**

50 步工具调用会产生大量上下文（预估 8K~15K tokens），需要分层管理：

```
┌─────────────────────────────────────────────────┐
│              上下文分层结构                        │
├─────────────────────────────────────────────────┤
│  L0: 系统提示 + 约束条件          (始终保留)      │
│  L1: 当前规划摘要                 (始终保留)      │
│  L2: 最近5步工具调用结果          (完整保留)      │
│  L3: 历史工具调用摘要             (压缩保留)      │
│  L4: 早期详细记录                 (滑动窗口淘汰)  │
└─────────────────────────────────────────────────┘
```

**2. 上下文压缩算法**

```python
class ContextCompressor:
    def compress(self, messages: List[Message]) -> List[Message]:
        """
        当上下文超过阈值时：
        1. 将 L4 层的详细工具结果压缩为一行摘要
           例: "POI搜索返回10个结果，选择了天安门、故宫、颐和园"
        2. 将 L3 层的多轮对话压缩为决策摘要
           例: "步骤3-8: 搜索了北京景点，确定了3个候选景点"
        3. 始终保留 L0/L1/L2 层完整信息
        """
        pass
```

**3. 关键信息追踪表**

在压缩上下文时，关键信息提取到结构化追踪表中，避免信息丢失：

```python
class ProgressTracker:
    """关键信息追踪表，独立于上下文窗口存在"""
```

#### 4.3.4 步骤控制与防退化

**1. 步骤预算管理**

```python
class StepBudgetManager:
    max_steps: int = 50

    def should_continue(self, state: TravelState) -> str:
        step = state["step_count"]

        if step >= self.max_steps:
            return "force_end"           # 强制结束

        if step >= self.max_steps * 0.8:  # 40步以后
            return "finalize"            # 进入收尾模式

        if self.detect_loop(state):      # 检测死循环
            return "break_loop"          # 打破循环

        return "continue"
```

**2. 死循环检测与打破**

```python
class LoopDetector:
    def detect_loop(self, recent_calls: List[ToolCall]) -> bool:
        """检测最近N次调用是否出现重复模式"""
        # 方法1: 连续3次相同工具+相同参数
        # 方法2: 5次调用中出现2次完全相同的调用
        # 方法3: 工具调用结果无实质变化（如反复搜索同一关键词）
        pass

    def break_loop(self, state: TravelState) -> str:
        """打破死循环的策略"""
        # 1. 切换到备用工具（如 amap → google）
        # 2. 修改搜索参数（扩大范围、更换关键词）
        # 3. 跳过当前子任务，继续后续任务
        # 4. 如果剩余步骤不足，直接进入收尾
        pass
```

**3. 决策退化防护**

随着步骤增加，模型可能出现决策退化（重复调用、无意义调用）。防护措施：

- **步骤质量评分**：每步工具调用后，评估该步是否推进了任务（信息增益 > 阈值）
- **惩罚机制**：在奖励函数中，对无推进的步骤施加负奖励
- **收尾模式**：步骤超过 80% 后，强制 Agent 进入"汇总现有信息 → 生成最终规划"模式

#### 4.3.5 LangGraph 状态图增强

```python
def create_travel_agent():

    # 原有节点
    workflow.add_node("analyze", analyze_node)
    workflow.add_node("think", think_node)
    workflow.add_node("use_tool", tool_node)

    # 新增节点：Long Horizon 支持
    workflow.add_node("compress_context", compress_node)    # 上下文压缩
    workflow.add_node("detect_loop", loop_detect_node)      # 死循环检测
    workflow.add_node("finalize", finalize_node)            # 收尾模式

    # 增强的条件边
    workflow.add_conditional_edges(
        "check_constraints",
        should_continue_v2,     # 增强版判断
        {
            "continue": "detect_loop",      # 先检测死循环
            "finalize": "finalize",          # 进入收尾
            "end": END
        }
    )
    workflow.add_conditional_edges(
        "detect_loop",
        loop_decision,
        {
            "normal": "think",              # 正常继续
            "loop_detected": "break_loop",  # 打破循环
            "need_compress": "compress_context"  # 需要压缩上下文
        }
    )
    workflow.add_edge("compress_context", "think")
    workflow.add_edge("finalize", END)

    return workflow.compile()
```

#### 4.3.6 训练阶段的 Long Horizon 特殊处理

**1. 课程学习（Curriculum Learning）**

训练按步骤数分阶段递增：

| 阶段 | 最大步骤数 | 训练重点 |
|------|-----------|----------|
| 阶段1 | 5~10步 | 单工具调用准确性 |
| 阶段2 | 10~20步 | 多工具协调 |
| 阶段3 | 20~35步 | 长程规划连贯性 |
| 阶段4 | 35~50步 | 完整Long Horizon能力 |

**2. 长程奖励塑形（Reward Shaping）**

```python
def long_horizon_reward(state: TravelState) -> float:
    base_reward = compute_base_reward(state)

    # 长程特有奖励项
    step_penalty = -0.01 * state["step_count"]          # 步骤越多，惩罚越大
    progress_bonus = +0.1 * progress_ratio(state)       # 推进度奖励
    loop_penalty = -0.5 * detected_loop_count(state)    # 死循环惩罚
    coverage_bonus = +0.2 * info_coverage(state)        # 信息覆盖度奖励

    return base_reward + step_penalty + progress_bonus + loop_penalty + coverage_bonus
```

### 6.2 奖励模型

```python
class RewardModel:
    def compute_reward(self, state: TravelState) -> float:
        # 任务完成奖励
        completion_reward = self.completion_reward(state)

        # 约束满足奖励
        constraint_reward = self.constraint_reward(state)

        # 工具调用效率奖励
        efficiency_reward = self.efficiency_reward(state)

        # 规划质量奖励
        quality_reward = self.quality_reward(state)

        # 加权求和
        total_reward = (
            0.3 * completion_reward +
            0.3 * constraint_reward +
            0.2 * efficiency_reward +
            0.2 * quality_reward
        )

        return total_reward
```

## 11. 设计审查记录

> 审查日期：2026-05-21
> 审查范围：全面审查（架构可行性、Long Horizon 实现、训练策略与数据）

### 11.1 致命问题（不解决项目无法推进）

#### P0-1：PPO 训练与 LangGraph 的集成缺失

**问题**：TRL 的 PPO 假设单轮文本生成（prompt → completion → reward），但本项目需要多步环境交互（model → tool call → env result → model → ...）。设计文档完全没有说明这个集成如何实现。

**影响**：训练流水线无法跑通。

**方案**：放弃 TRL 的 PPO 封装，自定义训练循环。每步做一次 forward + tool call + 收集 logprobs，episode 结束后用 GAE 计算 advantage 更新模型。

```python
class AgentPPOTrainer:
    def collect_episode(self, query, constraints):
        trajectory = []
        state = init_state(query, constraints)
        for step in range(max_steps):
            prompt = self.build_prompt(state)
            action, logprob = self.model.generate_with_logprob(prompt)
            tool_result = self.execute_tool(action)
            step_reward = self.compute_step_reward(state, action, tool_result)
            trajectory.append({"prompt": prompt, "action": action,
                               "logprob": logprob, "reward": step_reward})
            state = self.update_state(state, action, tool_result)
            if self.is_done(state):
                break
        return trajectory
```

#### P0-2：DPO 的 max_length=2048 严重不足

**问题**：50 步工具调用总长度约 25K~38K tokens，`max_length=2048` 只能覆盖约 3 步。

**影响**：DPO 训练完全无法处理长程 episode。

**方案**：`max_length` 改为 32768，或使用 packing 策略把多个短 episode 打包。

#### P0-3：奖励模型只给终态奖励，缺少步级奖励

**问题**：PPO 需要 per-step reward 来计算 advantage。当前设计只在 episode 结束后给一个总分，50 步只有 1 个 reward 信号，credit assignment 无法做。

**影响**：模型无法知道哪一步做得好、哪一步做得差。

**方案**：引入步级奖励 + GAE（Generalized Advantage Estimation）。

```python
def compute_step_reward(self, state, action, result):
    reward = 0.0
    reward += self.information_gain(result)      # 新信息增益
    reward += self.constraint_progress(state)     # 约束推进
    reward -= 0.01                                # 基础步骤惩罚
    if self.is_redundant(action, state):
        reward -= 0.1                             # 冗余调用惩罚
    return reward
```

### 11.2 重大问题（不解决训练效果会很差）

#### P1-1：奖励信号冲突

**问题**：`long_horizon_reward` 中 `step_penalty`（惩罚步骤多）与 `coverage_bonus`（奖励信息覆盖度高，但信息多=步骤多）直接矛盾，训练会震荡。

**方案**：去掉 `step_penalty`，改为"效率奖励"（信息增益 / 步骤数），不惩罚步骤多，而是奖励每步的产出。

#### P1-2：上下文长度被低估

**问题**：设计预估 "8K~15K tokens"，实际每步约 500~700 tokens，50 步 ≈ 35K~42K tokens。0.6B 小模型在超长上下文下注意力严重退化。

**方案**：
- 每步工具结果限制 200 tokens 以内（截断长结果）
- ProgressTracker 只注入关键摘要
- 目标控制在 20K tokens 以内（50 步 × 400 tokens）

#### P1-3：PPO 数据收集效率极低

**问题**：`batch_size=16`，每 episode 50 步 × 2s = 单次 PPO 更新需 1600 秒 ≈ 26 分钟。

**方案**：异步工具调用 + 并行收集 episode。模拟工具应去除随机延迟模拟（训练时设 delay=0），可降到 0.1s/步 → 单次更新 80 秒。

#### P1-4：ProgressTracker 与训练循环脱节

**问题**：ProgressTracker 存在于运行时状态，PPO 训练时模型只能看到文本上下文，无法直接访问。

**方案**：在 `build_prompt` 中把 ProgressTracker 关键信息序列化注入 prompt。

#### P1-5：上下文压缩由谁执行未定义

**问题**：`ContextCompressor.compress()` 方法体为空，未说明是模型自己压缩还是外部规则压缩。

**方案**：外部规则压缩（不依赖模型能力）。L4 层直接丢弃（信息已在 ProgressTracker 中），L3 层用正则提取关键信息生成一行摘要。

### 11.3 一般问题（需要补充）

#### P2-1：模型输出格式未定义

**问题**：未定义模型输出是 ReAct 格式、JSON 工具调用还是自由文本。

**方案**：采用 ReAct 格式（Thought/Action/Observation），结构清晰且适合 RL 训练。

#### P2-2：死循环检测误判率高

**问题**："连续 3 次相同工具+相同参数"——但更新约束后重新搜索是合法行为。

**方案**：加入上下文变化度检测，对比最近两次相同工具调用时的 state diff。

#### P2-3：课程学习如何控制步数未说明

**问题**：设计说"阶段1 最大 5~10 步"，但没说如何控制。

**方案**：用 `max_steps` 强制截断 + 未完成 episode 给中间奖励（不给 0 分）。

#### P2-4：训练数据缺少完整工具调用序列

**问题**：训练数据只有 `expected_tools`（工具名列表），冷启动 SFT 需要完整的 (state, action, observation) 序列。

**方案**：数据格式增加 `expected_tool_calls` 字段，包含完整的带参数调用序列和预期返回值。

### 11.4 审查结论总结

| 类别 | 数量 | 关键行动 |
|------|------|----------|
| 致命 | 3 | 自定义训练循环、修改 DPO 配置、引入步级奖励 |
| 重大 | 5 | 重设计奖励信号、控制上下文长度、异步并行收集 |
| 一般 | 4 | 定义输出格式、改进死循环检测、补充数据格式 |

**核心结论**：当前设计最大的问题是 **PPO 训练与 LangGraph Agent 的集成没有设计**。TRL 的 PPO 封装不支持多步环境交互，必须自定义训练循环。这是整个项目的技术核心，建议优先实现并验证。
